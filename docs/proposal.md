## 1. 概要

| 項目 | 内容 |
|---|---|
| タイトル | 未定（仮称: *Project Cardgame*） |
| ジャンル | 1対1 デッキ構築型デジタルカードゲーム（対AI専用） |
| 対戦形式 | プレイヤー vs AI。双方が自作デッキを持ち寄って対戦 |
| ゲームシステム | ラウンド制・交互行動（Legends of Runeterra 型）＋ 4列×前後2段のレーン配置 ＋ ラウンド終了時の同時戦闘 |
| プラットフォーム | 試遊版: Webブラウザ / 製品版: Godot（PC想定） |
| 制作体制 | 個人/趣味制作 |
| プレイ時間 | 1試合 10〜15分【仮】 |

### 1.1 コンセプト（一文）

**「まったく異なる世界の軍勢が、4本のレーンでぶつかり合う。配置の読み合いで勝つカードゲーム」**

### 1.2 ゲームの面白さの核

1. **配置の読み合い** — 双方が1手ずつ交互にユニットを置いていく。相手の配置を見てから置くか、先に置いて主導権を取るか。どのレーンのどの段に置くかが勝負を分ける。
2. **ラウンド終了時の同時戦闘** — 攻撃する側・守る側の区別はなく、ラウンドの最後に全レーンで一斉にぶつかる。組み上がった盤面の結果がそのまま出る。
3. **勢力ごとに違う世界観と戦い方** — 世界そのものが違う勢力同士が戦う。勢力によって「前列の壁で守る」「後列から撃つ」「空きマスを利用する」など、盤面の使い方がはっきり異なる。
4. **デッキ構築の自己表現** — 2つの勢力（2つの世界）を組み合わせてデッキを作る。
5. **待ち時間ゼロの対AI戦** — マッチング待ちや対人のストレスがなく、自分のペースで遊べる。

## 2. ターゲットとプレイ体験

- **ターゲット**: デジタルカードゲーム経験者（LoR、Hearthstone、MTG Arena等）で、対人戦の緊張や時間拘束を避けたい人。盤面を組み立てるタイプのゲーム（オートバトラー、タクティクス系）が好きな人。
- **提供したい体験**
  - 自分の配置が噛み合って、同時戦闘で一気に押し切ったときの気持ちよさ
  - 賢く動くAIとの読み合いで勝つ達成感
  - 負けたときに「配置やデッキをこう直そう」と思える納得感（AIが理不尽なズルをしない）

## 3. 世界観

### 3.1 基本設定

**複数の異なる世界が「狭間（はざま）」と呼ばれる場所で交わり、それぞれの世界の軍勢が衝突する**【仮】。

- 勢力ごとに **時代・技術水準・美術スタイル・カード名の付け方まで** 大きく変える。
  - 例: ファンタジーの騎士団とサイバーパンクの電脳都市が同じ盤面で戦う。
- 世界観の違いを **ゲームの仕組み上の違い（盤面の使い方）** と一致させ、見た目だけでなく遊び方でも個性が出るようにする。
- 異世界同士が交わる理由・「狭間」の正体は、ストーリー要素を入れる場合の軸にする（製品版以降）。

### 3.2 勢力案【仮】

製品版では5〜6勢力、試遊版ではそのうち2〜3勢力を実装する。

| 勢力（仮称） | 世界観 | 盤面での戦い方 | 試遊版 |
|---|---|---|---|
| 王国騎士団 | 中世ファンタジー。剣と盾、騎士道 | **前列の壁**。体力の高い前列ユニットと、隣のレーンを強化する「陣形」効果 | ○ |
| 電脳都市 | サイバーパンク。ハッカー、ドローン、企業傭兵 | **後列からの射撃**と、敵ユニットを別のマスへ動かす「ハッキング」 | ○ |
| 百鬼夜行 | 和風妖怪。夜の都、怪異 | **空きマスと死**を利用する。倒れると化けて出る、空いたマスに湧く | ○ |
| 深淵の眷属 | コズミックホラー / 深海 | **大型ユニット**。前後2マスを占有する巨体、相手に「狂気」を与える | — |
| 原初の森 | 原始の自然、獣と精霊 | **成長と連携**。同じレーンの前後に並べると強くなる | — |
| （予備枠）星間艦隊 | 宇宙SF | レーン全体に効く艦砲射撃、ラウンドをまたぐ遅延効果 | — |

## 4. ゲームルール（コア）

> 以下の用語・数値はすべて【仮】。

### 4.1 勝利条件

- 相手の **ライフ（初期20）** を0にする。
- 山札が尽きた状態でドローが必要になったプレイヤーは敗北。
- 同時戦闘で双方のライフが同時に0以下になった場合は、**ライフのマイナスが大きい側の負け**（例: −3 と −1 なら −3 の側が負け）。
  - マイナスの値もまったく同じ場合は **引き分け**【仮】。

### 4.2 盤面

各プレイヤーが **4列（レーン）× 前列・後列の2段 = 8マス** を持つ。レーンは相手の同じ番号のレーンと向かい合う。

```
            レーン1   レーン2   レーン3   レーン4
          ┌───────┬───────┬───────┬───────┐
 相手 後列 │       │       │       │       │
          ├───────┼───────┼───────┼───────┤
 相手 前列 │       │       │       │       │
          ╞═══════╪═══════╪═══════╪═══════╡  ← 戦線
 自分 前列 │       │       │       │       │
          ├───────┼───────┼───────┼───────┤
 自分 後列 │       │       │       │       │
          └───────┴───────┴───────┴───────┘
```

- 1マスにユニットは1体まで。
- **前列**: 戦闘で敵とぶつかる。攻撃役・壁役を置く場所。
- **後列**: 同じレーンの前列が倒れない限り、通常の攻撃からは守られる。支援役・射撃役を置く場所。
- **一度置いたユニットは、基本的に移動できない。** 移動できるのは、移動系のキーワードを持つユニットや、移動させるスペルを使ったときだけ（4.6）。そのため、どのマスに置くかの判断が重くなる。

### 4.3 ラウンドの流れ

攻撃権はなく、**毎ラウンドの終わりに双方のユニットが同時に戦う**。

```
[ラウンド開始]
  ├─ 双方: 最大マナ+1（上限10）、マナ全回復
  ├─ 双方: 1枚ドロー
  ├─ 先手トークンが一方に移る（毎ラウンド交互）
  │
[配置・行動フェイズ]  ← 先手トークンを持つ側から交互に1アクション
  │   アクション = ユニット配置 / スペル使用 / キーワード能力の起動 / パス
  │   ・双方が連続でパス → 戦闘フェイズへ
  │
[戦闘フェイズ]  ← 全レーンで同時に戦闘（4.4）
  │
[ラウンド終了]
  ├─ 「ラウンド終了時」効果の処理
  └─ 使い残したマナのうち最大3を「予備マナ」として持ち越し（スペル専用）
```

- 初期手札: 4枚。開始時に任意枚数を1回だけ引き直し（マリガン）可能。
- **先手トークン**: そのラウンドで最初に行動できる権利。先に置けば好きなマスを取れるが、相手に配置を見られてから対応される。先手・後手どちらにも利点がある作りにする。

### 4.4 戦闘の解決

戦闘は **全レーン同時** に解決する（ダメージをすべて計算してから一斉に適用する）。どちらが先に殴るかという有利不利をなくし、結果を予測しやすくする。

**攻撃の対象（各レーン内）**

| 攻撃するユニット | 攻撃対象 |
|---|---|
| 自分の前列 | 同じレーンの **敵の前列** → 空なら **敵の後列** → それも空なら **敵本体（ライフ）** |
| 自分の後列 | 通常は攻撃しない。「射撃」を持つユニットのみ、前列と同じルールで攻撃する |

- 前列同士は **互いに同時にダメージを与え合う**。
- 前列が空いたレーンでは後列がむき出しになり、前後とも空いたレーンは本体まで素通しになる。**前列の壁をどのレーンに置くか** が守りの判断になる。
- 前列がいる間に後列を狙えるのは、「貫通」（前列ユニットを倒した余剰ダメージが後列へ）などのキーワードやスペルのみ。
- 体力が0以下になったユニットは戦闘後にまとめて破壊される。
- 前列のユニットが破壊されても、後列のユニットは自動では前に出ない。

**例**（レーン2）

```
 相手 後列 : 弓兵 2/1 [射撃]
 相手 前列 : （空き）
 自分 前列 : 騎士 3/4
 自分 後列 : 僧侶 0/2
```

→ 騎士は相手の前列が空なので、相手の後列の **弓兵に3ダメージ**（弓兵は破壊）。弓兵も同時に射撃で自分の前列の **騎士に2ダメージ**（騎士は 3/2 で生き残る）。僧侶は攻撃しない。本体へのダメージはなし。

もしこのレーンの相手側が前列・後列とも空なら、騎士の3ダメージはそのまま **相手本体** に入る。

### 4.5 カードの種類

| 種類 | 説明 |
|---|---|
| ユニット | 盤面のマスに配置する。配置後は原則として移動しない。攻撃力/体力/キーワード能力を持つ。一部は前列専用・後列専用 |
| スペル | 使い切りの効果。自分の手番に使用し、**即時に解決** する。味方・敵のユニットを移動させるスペルもここに含む |
| 【検討】設置物 | マスに置く罠・建物（試遊版では見送り可） |

- 攻撃権を廃止し戦闘タイミングが固定になったため、v0.1にあったスペル速度とスタック（割り込み処理）は **試遊版では採用しない**。すべての効果を即時解決にしてルールと実装を単純にする。
- 相手の行動に反応する要素は、必要になったら「伏せて置き、条件を満たすと発動する罠」として追加を検討する。

### 4.6 キーワード能力の例【仮】

| キーワード | 効果 |
|---|---|
| 射撃 | 後列からでも攻撃できる（攻撃対象の順番は前列ユニットと同じ） |
| 貫通 | 敵の前列を倒した余剰ダメージが、同じレーンの敵後列（空なら本体）へ |
| 挑発 | 隣のレーンの敵前列ユニットの攻撃を、このユニットに引き付ける |
| 陣形 | 左右隣のマスの味方に効果を与える |
| 巨体 | 同じレーンの前後2マスを占有する |
| 機動 | 自分の手番のアクションとして、隣の空きマス（前後または左右）へ移動できる。1ラウンドに1回 |
| 押し出し | 配置時、同じレーンの敵前列ユニットを隣のレーンの空きマスへ動かす |
| 疾走 | 配置したラウンドの戦闘で、相手のユニットより先にダメージを与える |

### 4.7 デッキ構築ルール

- デッキ枚数: **40枚**、同名カードは **3枚まで**【仮】
- 1デッキにつき **最大2勢力** まで【仮】（例: 王国騎士団＋電脳都市のように、異なる世界を組み合わせる）

### 4.8 差別化要素

| 要素 | 状態 |
|---|---|
| **レーン制（4列×前後2段）** | **採用** |
| **ラウンド終了時の同時戦闘（攻撃権なし）** | **採用** |
| **勢力ごとに大きく異なる世界観** | **採用** |
| リーダー/チャンピオンの成長 | 検討中（勢力の看板ユニットとして相性がよい） |
| 地形/フィールドカード | 検討中（レーンごとに地形効果を付ける形なら盤面と噛み合う） |
| 予備マナの拡張 | 保留 |

## 5. 対戦AI

本作は対AI専用なので、**AIの質がそのままゲームの質になる**。最重要の技術要素として扱う。

### 5.1 方針

- **ズルをしない**: AIもプレイヤーと同じ公開情報だけで判断する（手札や山札の中身を覗かない）。
- **段階的に強くする**: 最初はシンプルなルールベースAIで動くものを作り、あとから探索型AIに置き換える。
- **難易度は「思考の深さ」で調整する**: ステータス補正などのズルで難しくしない。

### 5.2 実装段階

| 段階 | 方式 | 内容 |
|---|---|---|
| Lv1 | ルールベース | 優先度つきの行動ルール（「敵前列が強いレーンには壁役を置く」「空きレーンに攻撃役を置く」など） |
| Lv2 | 評価関数 + 戦闘シミュレーション | 各合法手について「このまま戦闘になったらどうなるか」を計算し、盤面評価が最大の手を選ぶ |
| Lv3 | 探索型 | 情報集合モンテカルロ木探索（ISMCTS）。相手の手札を確率的に推定して、相手の配置まで含めてシミュレーション |

### 5.3 レーン制・同時戦闘とAIの相性

- **良い点**: 戦闘がラウンド終了時に決まった手順で起こるため、「今の盤面で戦闘になったら何が起きるか」を正確に計算できる。Lv2の評価が作りやすい。
- **注意点**: 1枚のユニットにつき配置先が最大8マスあるので、選べる手の数が多い。探索では「明らかに悪い配置」（例: 射撃を持たない攻撃役を後列に置く）を事前に除外して手の数を絞る。

### 5.4 AI用デッキ

- 各勢力の組み合わせで、テーマのはっきりした **AIデッキを8〜10個** 用意【仮】。
- 将来は「プレイヤーのデッキ傾向に合わせてAIデッキを選ぶ」なども検討。

### 5.5 AI実装に必要な設計要件

- ゲームロジックが **UIから完全に分離** されていて、高速にコピー・シミュレーションできること。
- 「現在の状態で可能な合法手の一覧」を返すAPIがあること。
- 「戦闘フェイズだけを単独で計算する」APIがあること（AIの評価と、UIでの戦闘結果プレビューの両方に使う）。
- 乱数のシードを固定でき、同じ試合を再現できること（デバッグ・リプレイ用）。

## 6. UI・UX方針

- **戦闘結果のプレビュー**: 配置・行動フェイズ中、「今このまま戦闘になったら各レーンがどうなるか」（与えるダメージ、倒れるユニット、本体へのダメージ）を盤面上に常に表示する。同時戦闘のルールを直感的に理解できるようにし、読み合いに集中させる。
- 相手（AI）の行動は1手ずつ、何をどこに置いたかが分かるように見せる。
- 勢力ごとにカード枠・色・フォントを変え、世界観の違いが一目で分かるようにする。

## 8. 技術構成

### 8.1 二段階の開発方針

```
Phase A: ブラウザ試遊版               Phase B: Godot製品版
┌────────────────────────┐             ┌────────────────────────┐
│ UI: TypeScript + DOM/   │             │ UI: Godotシーン         │
│     Canvas (Vite)       │             │                         │
├────────────────────────┤  ロジック   ├────────────────────────┤
│ ゲームエンジン (TS)     │ ─ 移植 ──▶ │ ゲームエンジン (GDScript│
│ AI (TS)                 │             │  または C#)             │
├────────────────────────┤             ├────────────────────────┤
│ カードデータ (JSON)     │ ─ 共通 ──▶ │ カードデータ (JSON)     │
│ テストシナリオ (JSON)   │ ─ 共通 ──▶ │ テストシナリオ (JSON)   │
└────────────────────────┘             └────────────────────────┘
```

### 8.2 試遊版（ブラウザ）

- **言語/ツール**: TypeScript + Vite
- **描画**: まずはDOM + CSS（CSS Gridで4×4の盤面）で最低限のUIを作る（演出は後回し）
- **テスト**: Vitest（ルールエンジン、特に戦闘解決のユニットテストを厚めに）
- **配布**: GitHub Pages などで静的ホスティング
- **保存**: デッキはブラウザのlocalStorageに保存

### 8.3 Godotへの移行を楽にするための設計ルール

1. **ゲームロジックはUI・ブラウザAPIに依存しない純粋なモジュールにする**（状態 + アクション → 新しい状態）。
2. **カード効果はできる限りデータで表現する**（JSONのキーワード/効果定義）。コードで書く特殊効果は最小限にする。
3. **決定的（deterministic）に動くようにする**: 乱数はシード付きの自前RNGを使う。
4. **テストシナリオをJSONで共通化する**: 「初期盤面 + 操作列 → 期待する結果」を両エンジンで実行し、同じ挙動になることを確認できるようにする。戦闘解決は「盤面 → 戦闘後の盤面」のシナリオを多数用意する。
5. Godot側の言語は、TSからの移植しやすさとAI探索の速度を考えると **C#** が有力【仮】。GDScriptにする場合はAI探索の性能を検証する。

### 10.1 AI自動対戦によるバランス調整

対AI専用のゲームなので、**AI同士を自動で大量に対戦させる仕組み** を早い段階（M4）で作る。デッキ間の勝率、先手トークンを最初に持つ側の勝率、よく使われる/使われないカード、よく使われるマスを数値で確認し、バランス調整に使う。

## 11. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 同時戦闘で試合展開が単調になる（毎ラウンド同じ殴り合い） | 面白さの低下 | 移動系のキーワード・スペルや除去で盤面を動かす手段を各勢力に用意する。紙プロトタイプ（M0.5）で早期に確認する |
| 先手・後手の有利不利が偏る | バランス崩壊 | 先手トークンを毎ラウンド交互にし、AI自動対戦で勝率を監視する |
| 後列が安全すぎて、後列に強いユニットを溜め込む展開になる | 膠着 | 前列を倒せば後列を攻撃できるルールで緩和済み。加えて貫通・スペルなど後列に届く手段を各勢力に用意する |
| 基本の移動がないため、一度の配置ミスが取り返せず窮屈になる | ストレス、逆転の難しさ | 各勢力に少しずつ移動手段（キーワード・スペル）を用意する。戦闘結果プレビューで配置前に結果が分かるようにする |
| 配置先が多く、AIの探索が重い | テンポの悪化 | 明らかに悪い手を除外して手を絞る。思考時間に上限を設け、Web Worker/別スレッドで計算する |
| AIが弱い/不自然でつまらない | ゲームの面白さに直結 | 段階的に強化する。評価関数を調整しやすい作りにする |
| 勢力ごとに世界観が違いすぎて、全体の統一感がなくなる | 見た目の散漫さ | UIの共通部分（盤面・カードのレイアウト）は統一し、違いはカード枠・色・名前に集中させる |
| TS→Godotの移植コスト | 二重実装 | データ駆動設計 + 共通テストシナリオで差分を検出する |
| 個人制作のモチベーション維持 | 未完成で止まる | 早い段階で「遊べるもの」を作り、小さく公開してフィードバックをもらう |
