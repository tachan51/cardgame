## 1. 概要

| 項目 | 内容 |
|---|---|
| タイトル | 未定（仮称: *Project Cardgame*） |
| ジャンル | 1対1 デッキ構築型デジタルカードゲーム（対AI専用） |
| 対戦形式 | プレイヤー vs AI。双方が自作デッキを持ち寄って対戦 |
| ゲームシステム | ラウンド制・交互行動（Legends of Runeterra 型） |
| プラットフォーム | 試遊版: Webブラウザ / 製品版: Godot（PC想定） |
| 制作体制 | 個人/趣味制作 |
| プレイ時間 | 1試合 10〜15分【仮】 |

### 1.1 コンセプト（一文）

**「1手ごとに読み合う、ラウンド制の駆け引きを、いつでもAI相手に好きなだけ遊べるカードゲーム」**

### 1.2 ゲームの面白さの核

1. **交互行動による読み合い** — 相手ターン中に何もできないのではなく、1アクションごとに手番が入れ替わる。「今動くか、相手の出方を待つか」の判断が常に発生する。
2. **攻守が入れ替わるラウンド** — ラウンドごとに攻撃権が移り、「攻めるラウンド」と「守るラウンド」でプレイの組み立てが変わる。
3. **デッキ構築の自己表現** — 自分で組んだデッキでAIの用意したデッキに勝つ。構築とプレイの両方が腕の見せ所。
4. **待ち時間ゼロの対AI戦** — マッチング待ちや対人のストレスがなく、自分のペースで遊べる。

## 2. ターゲットとプレイ体験

- **ターゲット**: デジタルカードゲーム経験者（LoR、Hearthstone、MTG Arena等）で、対人戦の緊張や時間拘束を避けたい人。
- **提供したい体験**
  - 自分のデッキのコンボや戦略が決まったときの気持ちよさ
  - 賢く動くAIとの読み合いで勝つ達成感
  - 負けたときに「デッキをこう直そう」と思える納得感（AIが理不尽なズルをしない）

## 3. ゲームルール（コア）

> LoR型の「ラウンド制・交互行動」をベースに、独自の要素で差別化する。
> 以下の用語・数値はすべて【仮】。

### 3.1 勝利条件

- 相手の **ライフ（初期20）** を0にする。
- 山札が尽きた状態でドローが必要になったプレイヤーは敗北。

### 3.2 ラウンドの流れ

```
[ラウンド開始]
  ├─ 双方: 最大マナ+1（上限10）、マナ全回復
  ├─ 双方: 1枚ドロー
  ├─ 攻撃権トークンが一方に移る（毎ラウンド交互）
  │
[アクションフェイズ]  ← 攻撃権を持つ側から交互に1アクション
  │   アクション = ユニット召喚 / スペル使用 / 攻撃宣言 / パス
  │   ・双方が連続でパス → ラウンド終了
  │
[ラウンド終了]
  └─ 使い残したマナのうち最大3を「予備マナ」として持ち越し（スペル専用）
```

- 初期手札: 4枚。開始時に任意枚数を1回だけ引き直し（マリガン）可能。
- 後攻（第1ラウンドで攻撃権を持たない側）への補償を用意する【仮: 初期予備マナ+1】。

### 3.3 攻撃と防御

- 攻撃権を持つプレイヤーは、自分の手番に **攻撃宣言** ができる（1ラウンド1回）。
- 攻撃側は場のユニットから攻撃者を選んで前に出す。
- 防御側は各攻撃者にブロッカーを割り当てる（割り当てなければ本体へダメージ）。
- 戦闘前に、双方が交互に **スペル（速攻・瞬間）** で対応できる。
- 戦闘の解決: 対面したユニット同士が同時にダメージを与え合う。

### 3.4 カードの種類

| 種類 | 説明 |
|---|---|
| ユニット | 場に出て攻撃・防御を行う。攻撃力/体力/キーワード能力を持つ |
| スペル | 使い切りの効果。**速度**を持つ（下表） |
| 【検討】装備/遺物 | ユニットに付与する持続効果（試遊版では見送り可） |

| スペル速度 | 使えるタイミング | 相手の対応 |
|---|---|---|
| 通常 | 自分の手番、戦闘外のみ | 可能 |
| 速攻 | 自分の手番ならいつでも（戦闘中も可） | 可能 |
| 瞬間 | いつでも | 不可（即時解決） |

※ 効果はスタック（後入れ先出し）で解決。双方がパスした時点で上から順に解決する。

### 3.5 デッキ構築ルール

- デッキ枚数: **40枚**、同名カードは **3枚まで**【仮】
- **勢力（リージョン）**: 5〜6勢力を用意し、1デッキにつき最大2勢力まで【仮】
  - 勢力ごとに明確な戦略の色（例: 速攻型 / 除去・コントロール型 / 大型ユニット型 / 墓地・リソース活用型 など）

### 3.6 差別化要素（独自色の候補）

LoRのクローンにならないよう、以下から1〜2個を採用して独自性を出す。

| 案 | 内容 | 狙い |
|---|---|---|
| A. 地形/フィールドカード | ラウンドごとに場の状況が変わり、特定勢力が有利になる | 毎試合の展開に変化 |
| B. リーダー/チャンピオンの成長 | 条件達成でレベルアップする看板ユニット | デッキの「顔」と目標を作る |
| C. レーン制 | 場を2〜3レーンに分け、配置が戦略になる | 盤面の読み合いを深くする |
| D. 予備マナの拡張 | 予備マナでユニットも出せる/特殊能力を起動できる | リソース管理を独自化 |

→ 試遊版では **B（リーダー成長）** をまず採用し、他は検証してから判断するのを推奨。

## 4. 対戦AI

本作は対AI専用なので、**AIの質がそのままゲームの質になる**。最重要の技術要素として扱う。

### 4.1 方針

- **ズルをしない**: AIもプレイヤーと同じ公開情報だけで判断する（手札や山札の中身を覗かない）。
- **段階的に強くする**: 最初はシンプルなルールベースAIで動くものを作り、あとから探索型AIに置き換える。
- **難易度は「思考の深さ」で調整する**: ステータス補正などのズルで難しくしない。

### 4.2 実装段階

| 段階 | 方式 | 内容 |
|---|---|---|
| Lv1 | ルールベース | 優先度つきの行動ルール（「出せる中で最もコストの高いユニットを出す」など） |
| Lv2 | 評価関数 + 1手読み | 合法手を全列挙し、盤面評価（ライフ差、盤面戦力、手札枚数など）が最大の手を選ぶ |
| Lv3 | 探索型 | 情報集合モンテカルロ木探索（ISMCTS）。相手の手札を確率的に推定してシミュレーション |

### 4.3 AI用デッキ

- 各勢力の組み合わせで、テーマのはっきりした **AIデッキを8〜10個** 用意【仮】。
- 将来は「プレイヤーのデッキ傾向に合わせてAIデッキを選ぶ」なども検討。

### 4.4 AI実装に必要な設計要件

- ゲームロジックが **UIから完全に分離** されていて、高速にコピー・シミュレーションできること。
- 「現在の状態で可能な合法手の一覧」を返すAPIがあること。
- 乱数のシードを固定でき、同じ試合を再現できること（デバッグ・リプレイ用）。

## 6. 技術構成

### 6.1 二段階の開発方針

```
Phase A: ブラウザ試遊版               Phase B: Godot製品版
┌────────────────────────┐             ┌────────────────────────┐
│ UI: TypeScript + DOM/   │             │ UI: Godotシーン         │
│     Canvas (Vite)       │             │                         │
├────────────────────────┤  ロジック   ├────────────────────────┤
│ ゲームエンジン (TS)     │ ─ 移植 ──▶ │ ゲームエンジン (GDScript│
│ AI (TS)                 │             │  または C#)             │
├────────────────────────┤             ├────────────────────────┤
│ カードデータ (JSON)     │ ─ 共通 ──▶ │ カードデータ (JSON)     │
│ テストシナリオ (JSON)   │ ─ 共通 ──▶ │ テストシナリオ (JSON)   │
└────────────────────────┘             └────────────────────────┘
```

### 6.2 試遊版（ブラウザ）

- **言語/ツール**: TypeScript + Vite
- **描画**: まずはDOM + CSSで最低限のUIを作る（演出は後回し）
- **テスト**: Vitest（ルールエンジンのユニットテストを厚めに）
- **配布**: GitHub Pages などで静的ホスティング
- **保存**: デッキはブラウザのlocalStorageに保存

### 6.3 Godotへの移行を楽にするための設計ルール

1. **ゲームロジックはUI・ブラウザAPIに依存しない純粋なモジュールにする**（状態 + アクション → 新しい状態）。
2. **カード効果はできる限りデータで表現する**（JSONのキーワード/効果定義）。コードで書く特殊効果は最小限にする。
3. **決定的（deterministic）に動くようにする**: 乱数はシード付きの自前RNGを使う。
4. **テストシナリオをJSONで共通化する**: 「初期状態 + 操作列 → 期待する結果」を両エンジンで実行し、同じ挙動になることを確認できるようにする。
5. Godot側の言語は、TSからの移植しやすさとAI探索の速度を考えると **C#** が有力【仮】。GDScriptにする場合はAI探索の性能を検証する。

### 8.1 AI自動対戦によるバランス調整

対AI専用のゲームなので、**AI同士を自動で大量に対戦させる仕組み** を早い段階（M4）で作る。デッキ間の勝率、先攻/後攻の勝率、よく使われる/使われないカードを数値で確認し、バランス調整に使う。

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 交互行動ルールの実装が複雑（スタック、割り込み） | 開発の遅れ、バグ | M1でルールエンジンを単体で作り込み、テストを厚くする |
| AIが弱い/不自然でつまらない | ゲームの面白さに直結 | 段階的に強化する。評価関数を調整しやすい作りにする |
| AIの思考が遅い（探索型） | テンポの悪化 | 思考時間に上限を設ける。Web Worker/別スレッドで計算する |
| TS→Godotの移植コスト | 二重実装 | データ駆動設計 + 共通テストシナリオで差分を検出する |
| 既存タイトルに似すぎる | 独自性の欠如、権利面の懸念 | 用語・数値・カードを独自に設計し、差別化要素（3.6）を採用する |
| 個人制作のモチベーション維持 | 未完成で止まる | 早い段階で「遊べるもの」を作り、小さく公開してフィードバックをもらう |
